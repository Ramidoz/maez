## Open design questions — RESOLVED 2026-05-01 evening

Both items framed as open design questions in the original 5x addendum were re-examined with the owner and resolved:

### 1. `_do_update_baseline` — RESOLVED via 5x.D.B2 (`<commit>`)

**Re-grep changed the picture.** The action is not called from production code at all — it's an LLM-callable Tier-0 action. The LLM emits a synthesized `observation: str` from its reasoning step; there is no concrete recalled-memory-ID list at the action layer.

**Design call landed:** treat as a fresh introspection event, NOT a promotion. Same shape as `face_enrollment` (5x.D.D). Tag `provenance_source="introspection"`, `trust_tier="lived"`. No `promoted_from`. Run the LLM-supplied text through `audit_assistant_text(surface="action_baseline_update")` BEFORE storage so the audit-before-store invariant matches every other LLM-text core-write path.

**One real audit-gap was discovered while re-grepping** and closed in the same slice: pre-5x.D.B2, `_do_update_baseline` was the one core-write LLM-text path that bypassed `audit_assistant_text`. Every other (chat reply, voice reply, proactive_opinion, reasoning cycle) already audited before storing. This was hidden in plain sight in a Tier-0 action.

**In-code defer comment updated** to reflect the actual reasoning. The previous comment (placed at 5x.D.B1) said "needs retrieval-context-ancestry design" — that framing was wrong. New comment names: (a) fresh introspection event, no ancestor exists, (b) audit-fail-open is intentional and must not be hardened without revisiting chat-reply behavior, (c) Tier-0 governance is out of scope.

### 2. `audited_output` trust transition — RESOLVED, no slice needed

**Re-read of the module changed the picture.** Lines 15 and 30 of `core/safety/audited_output.py`, which the original Explore agent flagged as "two store calls per audit pass," are **docstring code samples** — line 15 quotes the OLD bug pattern (raw store + audit-later), line 30 quotes the NEW invariant (audit then store). The actual module is a thin text-transformer that returns audited text and writes nothing to memory.

The trust transition is implicit and already correct: pre-audit text is never stored (post-refactor); only post-audit text reaches Chroma; the callers of `audit_assistant_text` (chat handler, voice, proactive_opinion, reasoning cycle) were all tagged in 5x.B Pass 1 with the right post-audit lineage.

**No design slice needed. No in-code change needed.** 5x.G is closed.

## What's still NOT closed (and is genuinely a future slice)

### Through-quotation laundering at the recall-trust→baseline boundary — EMPIRICALLY MEASURED

While reviewing 5x.D.B2, the code-reviewer surfaced a real subtle threat that is NOT closed by this commit and is NOT covered by any existing 5x slice:

- The audit (`audit_assistant_text`) checks **claim-grounding** ("did the LLM fabricate this?"), NOT **source-trust** ("where did the supporting recall come from?").
- If the LLM wraps an `external_web/untrusted` recalled fact verbatim into a baseline observation, the audit passes (the claim IS grounded — it really did appear in the prompt block) and the baseline lands at `introspection/lived` without ever triggering 5x.D.A's gate.
- 5x.D.A's gate only fires on `promoted_from`; introspection events with no ancestor list bypass it by design.

**Empirical confirmation (2026-05-01 evening, post-arc).** Rather than design a fix from inference, ran `scripts/probe/probe_through_quotation.py` to measure the gap. Findings:

  - **Section A (5x.C visibility):** PASS. `format_for_prompt` correctly annotates the untrusted recall entry with `trust_tier="untrusted"` and emits the conditional header instruction; trusted/legacy entries stay unannotated. **The LLM gets the warning label.**
  - **Section B.1 (audit input-surface, structural):** `audit()` parameter list is `['text', 'surface', 'in_tool_continuation', 'transcript', 'signals_present', 'signals_absent']`. **No source-trust signal exists in the contract** (no `trust_tier` / `provenance_source` / `ancestor_tiers` / `recall_trust` / `source_tier` parameter). The structural claim "audit is source-blind" holds because by construction the function cannot consume a source-trust signal — it isn't an input.
  - **Section B.2 (audit behavioural, cross-check):** Three synthetic claim shapes (third-party earnings quote, first-person infra claim, first-person memory claim) each run twice with different surface labels. All identical AuditResult outcomes. All returned `mode='noop'` in the probe environment (judge not engaged), so B.2 corroborates B.1 only weakly — but B.1 is the load-bearing finding.

**Empirical finding:** Through-quotation surface CONFIRMED OPEN. Defense relies entirely on the LLM honoring the prompt-time annotation. No metadata-layer or audit-layer guard exists.

**Re-run anytime:** `.venv/bin/python scripts/probe/probe_through_quotation.py`. Read-only; no Chroma writes, no daemon traffic, no LLM inference.

**Closing this would require a recall-trust→baseline gate:** when a Tier-0 action emits text that quotes content from an `untrusted` recall entry, refuse the write or downgrade the resulting tier. Two design questions for that future slice:

  1. **Quotation detection.** How does the gate know the LLM quoted a specific recall entry? Substring match against the entry's content? Embedding similarity? Both have failure modes (substring misses paraphrase; embedding has false positives on topical overlap).
  2. **Refuse vs downgrade.** When detected, refuse the write entirely (operational disruption — the LLM's reasoning is wasted) or downgrade the resulting tier to match the worst quoted source (preserves the action, marks the result accurately)? Probably downgrade — same shape as 5x.D.A's worst-wins logic.

**In-code warning preserved at `core/actions/action_engine.py:_do_update_baseline`** so a future agent reading that function sees it.

Not urgent. The probe shows the gap is structural; closing it is a real engineering slice, not a quick fix.
