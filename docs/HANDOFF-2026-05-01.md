## Open design questions — DO NOT just patch

These are the two items that look like "more wiring" but are actually design slices. Wiring them naively re-opens the laundering surface 5x just spent ten commits closing.

### 1. `_do_update_baseline` retrieval-context ancestry

**File:** `core/actions/action_engine.py:1098`. The action receives `observation: str` — a synthesized string, not a list of recalled memory IDs. To wire through `promoted_from` requires upstream changes to whoever *constructs* the observation, capturing which retrieval hits shaped it.

**Why a stub ancestor is the wrong shortcut:** if you pass `promoted_from=[<top-1-hit>]`, you defeat worst-wins on multi-source retrievals (the 5x.D.A reviewer's forward-look). If you pass `promoted_from=[]`, the gate raises (5x.D.A treats empty as a programming error). Either way you've pretended ancestry where there is none in scope.

**Real questions for the next slice:**
- Where does the retrieval window live, and at what point is its ID list serializable through to `_do_update_baseline`?
- All-of-window or top-k? On a 50-row retrieval window with one untrusted hit, what's the right behavior — refuse, downgrade, or filter-then-promote?
- Does the action API need to grow a new param (`source_memory_ids: list[str]`)?
- Is there an opt-in path for owner-acknowledged baseline updates that cite untrusted material? (Probably no — but record the call.)

**In-code marker preserved:** `core/actions/action_engine.py:1098` carries an explicit defer comment placed at 5x.D.B1. A future agent reading just that function knows the missing `promoted_from` is intentional and is warned NOT to "fix" it without designing the multi-source citation properly.

### 2. `audited_output` trust transition

**File:** `core/safety/audited_output.py:15, 30`. Two `store()` calls per audit pass — one for the unaudited LLM output, one for the audited version. They have *different* lineage:
- Pre-audit text is closer to `claude_tier_response/untrusted` (raw local model output, not yet validated against the safety pipeline).
- Post-audit text is closer to `introspection/lived` (Maez's own audited voice).

**The audit IS the trust transition.** Designing this as a fall-back-tier-promotion (untrusted → lived after audit pass) couples 5x.D.A's gate logic to the audit's success/failure. Wrong shape:
- Every audit becomes a promotion-gate event → expensive on the hot path.
- Audit-passes-by-default → silent untrusted-to-lived laundering.

**Real questions for the next slice:**
- Does the audit subsystem already report a binary pass/fail signal that's stable and trustworthy enough to flip a tier on?
- Is this `audited_output` a separate slice (`5x.G`?) or does it fold into the broader 5x.D pattern?
- Should audited_output writes carry a new metadata field (`audit_pass: bool`) so 5x.D.A's gate can read it as a covenant-grade override of the upstream `untrusted` lineage?

This needs a deliberate scoping conversation with the owner before code.
