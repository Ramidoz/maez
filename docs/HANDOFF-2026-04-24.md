## The one pattern that connects four bugs this session

**Autonomous processes write to user-visible surfaces without routing
through the audit stack.** Interactive paths (`handle_message`, web
`/chat`) all go through `core.safety.audited_output.audit_assistant_text`
+ `core.safety.output_command_guard`. Scheduled or daemon-triggered
paths historically did not. Today caught four:

| Path | Bug shape |
|---|---|
| `skills/github_publish._write_readme` | Nightly 23:00 regen from hardcoded template → "Built By: the owner" + wiped deliberate README voice |
| `_send_morning_briefing` | LLM-generated briefing → direct telegram send, hardcoded `/home/rohit/maez/...` path, "sending the owner his..." in prompt |
| `DreamState.run_dream_cycle` | LLM insight → direct telegram send, zero backstop |
| Presence-return greeting | Hardcoded `"Welcome back the owner."` string, no thread continuity |

All four patched this session. The meta-level lesson:
**every scheduled or daemon-triggered text-emitting path is a
regression candidate**. F3 (training proposal) + F5 (github commit
message) are the known remaining ones. Others may lurk — the audit
doc's Method section describes the repeatable grep + classify pass
that surfaced these.

### The autonomous-surface audit pattern

When a new surface-write regression appears, before patching the
symptom, grep for every callsite of `telegram.send_message`,
`_ws_broadcast`, `store_telegram`, and `github_publish`. For each,
classify:
- Content source: deterministic template vs LLM-generated
- Audit status: does it call `audit_assistant_text` before the write?
- Voice hygiene: does it hardcode "the owner" / "Rohit"?
- Continuity: is Maez-initiated output stored in a form
  `_clean_exchange` can thread into `chat_history`?

Full method in `docs/audit_2026-04-24/autonomous_surface_audit.md`.

### The chat_history threading contract

As of `cc462c5`, `daemon.handle_message` accepts an optional
`chat_history` kwarg; the Telegram adapter passes the last 3 cleaned
exchanges; `core.brain.conversation_history.history_to_messages`
parses them into alternating user/assistant messages between the
system prompt and the current turn. Any new surface that wants
continuity threading needs to wire through the same kwarg.

As of `a7f99fb`, `_clean_exchange` handles BOTH storage formats:
- Daemon: `"the owner (<src>): X\n[envelope]\nMaez: Y"`
- Web + voice: `"the owner asked: X\nMaez replied: Y"`

Operational storage (card state summaries, recovery markers) passes
through unchanged and the downstream parser rejects — correct, they
aren't conversational turns.

### `display_name()` is the owner-name source of truth

`core.memory.identity.display_name()` returns the configured owner
name ("Rohit" on this install, "Friend" by default). Every
surface-visible string that names the owner must resolve from this
helper, not hardcode. Same rule applies to anyone parsing stored
exchanges — use prefix-agnostic splitting (first `:` of line 1), not
a literal name match.
