## What Changed

Valence v0.2 adds the resolved-only want-progress channel to the live thermometer.
The slice keeps the pure `core/evolution/valence/` package untouched and wires only the honest signal that exists today: `satisfied` want events since the previous valence pulse.

Three touch points:

- `core/evolution/wants.py`
  - Added `Wants.count_events_since(since_ts, event_type)`.
  - Read-only `SELECT COUNT(*) FROM want_events WHERE ts > ? AND event_type = ?`.
  - Validates `event_type` against `EVENT_TYPES`; unknown types such as `blocked` raise `ValueError`.
  - Uses a read-only SQLite URI.

- `core/evolution/valence_live.py`
  - Added `last_pulse_epoch(log_path=None)`.
  - Converts the last valence JSONL record's ISO timestamp to epoch seconds before it can be compared to `want_events.ts`.
  - Rejects naive timestamps instead of interpreting them in host-local time.
  - Threads `resolved` into `WantSignals`.
  - Adds `want_coverage`:
    - `resolved: satisfied_events_delta`
    - `blocked: not_live_derived`
    - `stale: not_live_derived`

- `daemon/maez_daemon.py`
  - At the existing wake-gated end-of-cycle valence read, the daemon reuses its existing `daemon.wants` object.
  - It checks `daemon.wants` before reading the valence cursor, so no-wants callers remain hermetic.
  - If a cursor exists, it calls `daemon.wants.count_events_since(cursor, "satisfied")`.
  - Any cursor/wants-read failure degrades to `resolved=0` and the heartbeat continues.
  - No raw daemon SQL against `want_events`; no new `Wants(...)` construction in the heartbeat path.
