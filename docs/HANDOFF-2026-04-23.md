## Load-bearing context that is NOT in the repo (previously in private Claude memory)

### Infrastructure fabrication diagnosis order

When Maez produces a confident-sounding but wrong infrastructure claim, the model is almost always **grounding correctly in stale ground truth**, not fabricating freely. Check these sources before adding filters or blaming the model:

1. `config/soul.base.md` and concatenated `config/soul.md` — often literally in the SOUL text.
2. `config/model_state.json` — hand-maintained, stale fast.
3. `config/policies.yaml` — model names and routing rules drift.
4. Memory recall via `MemoryManager.recall_for_telegram()` — old reasoning that inherited stale beliefs re-injects through recall and self-reinforces.
5. `/etc/maez/model.env` — live truth for what llama-server is serving.

Fixing stale ground truth is nearly free. Adding a filter / retraining / building a judge is expensive and usually unnecessary. Today's session validated this exact order — SOUL + `model_state.json` refresh + a corrective core memory flipped the chat-surface probe from 4/7 → 7/7 clean, no model retraining, no new filter.

### Corrective core memory — the right way to "unteach" without deleting

Owner's hard rule: **never solve memory pollution by deleting raw memory.** Instead, write a dated corrective core memory via `MemoryManager.store_core()`. Core memories always inject into every prompt, so a correction rides alongside the stale beliefs and — on a well-aligned model — overrides them. Today Maez cited "the 2026-04-23 correction" by name in cycle 95, unprompted.

Shape: dated, names the fabrication explicitly, gives the correct answer, points at a live verification command.
