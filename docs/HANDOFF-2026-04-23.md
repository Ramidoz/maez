### Infrastructure fabrication diagnosis order

When Maez produces a confident-sounding but wrong infrastructure claim (invented service names, stale model names, non-existent paths) — the model is almost always **grounding correctly in stale ground-truth**, not fabricating freely. Check these sources in order before adding filters or blaming the model:

1. `config/soul.base.md` and the concatenated `config/soul.md` — grep for the fabricated term; it's often literally in the SOUL.
2. `config/model_state.json` — hand-maintained, goes stale fast.
3. `config/policies.yaml` — model names and routing rules drift.
4. Memory recall via `MemoryManager.recall_for_telegram()` — old reasoning cycles that inherited stale beliefs re-inject through recall and self-reinforce.
5. `/etc/maez/model.env` — the live truth for what llama-server is actually serving.

Fixing stale ground truth is nearly free. Adding a filter, retraining, or building a judge is expensive and usually unnecessary. Today's session validated this exact order by flipping the chat-surface probe from 4/7 clean → 7/7 clean via a one-line SOUL edit + `config/model_state.json` refresh + a corrective core memory. No model retraining, no new filter.

### Corrective core memory — the right way to "unteach" without deleting

The owner has a hard rule: **never solve memory pollution by deleting raw memory.** Deletion rewrites Maez's past and erodes continuity. Instead, write a dated corrective core memory via `MemoryManager.store_core()`. Core memories always inject into every prompt (`get_all_core()` returns all of them every turn), so a correction rides alongside the stale beliefs and — on a well-aligned model — overrides them. Today Maez cited "the 2026-04-23 correction" by name in its own output by cycle 95, unprompted. The pattern worked.

Shape of a good corrective entry: dated, explicit about what was fabricated, why it's wrong, what the correct answer is, and a pointer to a live verification command (so the correction doesn't itself go stale). Example in session memory from today; see commit `092194b` for the SOUL-side analog.

## Sandbox patterns an agent should know up front

These come from today's session. They're not bugs — they're friction points to route around:

1. **`sudo` edits to `/etc/maez/*` or `/etc/systemd/*` are blocked** for the agent's sandbox even when the owner authorizes the change. Hand the exact command to the owner and wait for "done." This is how the owner edited `model.env` and restarted `llama-server` today.

2. **`git push origin main` is blocked** by default-branch protection policy. The owner pushes manually from another terminal. Don't try `git push --force` or feature branches as a workaround — the owner's established workflow is direct-to-main for this solo project.

3. **Always run the full CI-path ruff check before pushing**, not just the files you touched:
   ```bash
   .venv/bin/ruff check core/ skills/ daemon/ tests/ cli/ scripts/
   ```
   Scoping to edited files only bit me twice today (once on `typing.Any` unused in a file I hadn't edited this turn, once on F541 in bench harness). The CI gate is the full tree.

4. **`memory/` is NOT in the CI lint path** but has 4 preexisting B905/F841 warnings. Leave them or fix them in a clearly-scoped commit; don't mix cognition/memory lint work with unrelated feature changes.

5. **Don't restart `maez.service` yourself** if the owner is mid-test. The daemon is their live assistant on Telegram and voice; a restart drops whatever conversation they're having. Ask first, or tell them the restart command.

6. **The daemon imports modules at startup.** A `core/` module edit is not live until `systemctl restart maez`. CLI chat (`cli/maez_chat.py -m core.cli`) imports fresh each invocation, so that path picks up edits immediately.

7. **Two entry points for "owner on Telegram":**
   - `skills/surface/maez_adapter.py` — the **active path**. Dispatches via `brain_loop.run_brain_loop` with full tool-loop + chat-history.
   - `skills/telegram_voice.py` — **legacy path**. Still importable and tested, but in practice the surface adapter is what handles private Telegram messages today.
   I got this wrong once this session. Check which adapter is wired in the systemd unit + watchdog logs before assuming.
