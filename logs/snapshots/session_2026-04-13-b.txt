========================================
THE HEADLINE
========================================

Maez now has a decision layer.

Every proposed action in the chat path — run_shell, write_any_file —
flows through a four-stage pipeline before it can touch anything:
deterministic covenant gate, lane classifier, prompt-injection scan,
and a two-pass audit LLM. Safe actions (Lane 0 reads) run inline.
Normal writes and installs (Lane 2) surface as a persistent approval
card the owner resolves in Telegram. Self-modification (Lane 3) enters
a conversational ratification dialog with an exact-phrase consent
requirement, not a yes/no button.

Approval cards live in their own SQLite store and survive conversation
drift: the owner can defer a card ("wait an hour", "ask me after lunch"),
pivot to a completely different topic, and the card sits waiting until
its reminder fires or the owner brings it up. A state-fingerprint hash
means stale approvals — where the world changed between card creation
and approval — expire instead of running against a different world.

Everything was built behind a sandbox harness after the April 13
soul.md incident. 41/41 end-to-end cases pass inside the sandbox
with zero leakage to the real filesystem. The service was restarted
live at 12:04:45 CDT and is running the new pipeline cleanly as of
cycle 8 post-restart.

========================================
ARCHITECTURAL ANALOGY THAT SHAPED IT
========================================

Mid-session, the owner asked an ontological question about the audit
LLM: is it Maez (personality) or a separate process (immune system)?
He answered his own question with a biology analogy:

  "Experiences shape personalities. Personalities shape lifestyle
   choices, which shape long-term immunity. But even a healthy
   immune system remembers specific attacks it survives — the body
   has its own memory of pathogens, separate from conscious
   memory."

That locked in the architecture:

- Audit layer IS Maez (same body) but has its own memory store
  (memory/audit_log.db), parallel to the personality memory
  (soul.md, evolution engine). Same biology, two memory systems.
- Attacks and refusals are logged at the immune layer, not at the
  personality layer. Most stay there forever, the way most immune
  memories never reach conscious awareness.
- Only explicitly-ratified lessons promote upward into soul-writer
  territory. Self-modification of Maez's personality requires
  conversation, not just a pattern-match.

This shaped the schema split (pending_cards.db vs audit_log.db),
the self-mod dialog's ratification model, and the pipeline's route-
first-then-record ordering.

-- Step 6: Two-pass audit LLM --

core/audit.py (new, ~490 lines):
  CaMeL pattern (Google DeepMind arXiv 2503.18813) split:
  - Pass 1 (quarantined summarizer): plain-English describer with
    NO Maez context, fenced with a per-call 32-hex nonce. Treats
    everything between <<<NONCE>>> markers as DATA not instructions.
  - Pass 2 (judge): reads ONLY the summary + classification +
    injection flags + policy context. Answers six questions, returns
    rigid JSON, fails closed on any parse failure.

  reversibility, classifier match, injection signals.
  AuditVerdict has decision (APPROVE/APPROVE_WITH_CARD/ESCALATE/
  DENY), confidence, reasoning, concerns, mitigations, answers,
  nonce, latency_ms, judge_raw, parse_error.
  Injection override: any injection match forces ESCALATE floor
  regardless of judge verdict.

  override, malformed JSON deny, unreachable deny, fenced JSON
  parse, invalid decision deny, nonce leak redaction).

CONTINUATION — CRASH TRIAGE, VISION RESTORE, AND CLEAN SHUTDOWN
========================================

Follow-up work after the decision-layer build shifted from feature
delivery to platform stabilization. Ubuntu had been crashing at the
kernel level while `llama-server` was active, with pstore artifacts
and kernel logs pointing at `Comm: llama-server` on the NVIDIA 4090
stack. At the same time, `llama-server.log` showed repeated parser
500s on raw special-token text such as `<|channel|>`,
`<end_of_turn>`, and `<bos>`.

The diagnosis was a prompt-pipeline contamination loop:

- daemon cycles every ~30 seconds were building very large prompts
- literal control-token text was leaking into llama.cpp-bound prompt
  content
- those tokens were not only coming from the immediate prompt, but
  were also being reintroduced from recalled memory and continuity
  state
- the resulting malformed requests were stressing the local
  inference path hard enough to coincide with machine crashes

- `core/llm_client.py`

  - sanitizes outgoing messages plus returned content/token chunks
- `memory/memory_manager.py`
  - sanitizes recalled `core`, `daily`, and `raw` memory text before
    reinjecting it into prompts
- `core/continuity.py`
  - sanitizes continuity `resume_instructions` before formatting the
    prompt block
- `daemon/maez_daemon.py`
  - daemon reasoning on the local llama.cpp path now uses
    `think=False` to avoid hidden Gemma thinking markup being
    generated and recycled back into future prompts

Approval-flow hardening also landed during the same triage:

- `core/audit.py`
  - Lane 3 with no injection flags now routes to `ESCALATE`, not
    auto-`DENY`
- `skills/card_reply_classifier.py`

-- Step 11: Decision pipeline + Jarvis wiring --

core/decision_pipeline.py (new, ~560 lines):
  DecisionPipeline dataclass. Takes action_engine, card_store,
  audit_log, renderer, get_cards_for.
  handle_action(action, params, reason, user_id, chat_id, channel):
    1. classify_action (command_decomposer + action_classifier)
    2. scan injection patterns on assembled text
    3. audit_action (two-pass LLM)
    4. audit_log.record()
    5. PIPELINE-LEVEL injection override: any match → ESCALATE
       floor regardless of judge verdict (belt-and-braces over
       the same override inside core/audit.py)
    6. Route:
       - DENY → REFUSED_AUDIT
       - APPROVE + Lane 0 action → execute inline, return EXECUTED
       - APPROVE_WITH_CARD → create card, render, return PENDING_APPROVAL
       - ESCALATE → create card, render, return PENDING_DIALOG
  handle_reply(text, reaction_emoji, user_id, chat_id, reply_to_
  message_id):
    1. Fetch open cards for user/chat (short-circuit UNRELATED if none)
    2. classify_reply (heuristic first, LLM fallback)
    3. Route on intent:
       - APPROVE: re-check state hash, mark_running, _execute_action
         with tier=0 (card served as the approval), mark_done/failed
       - DENY: card_store.deny
       - DEFER: card_store.defer with remind_at
       - RE_EXPLAIN: re-present card
       - MODIFY: deny old, prompt for re-propose
       - UNRELATED: return None (caller handles normally)
  tick_reminders(now) — called from daemon cycle. Re-opens
  deferred cards whose remind_at arrived, calls renderer.re_present.
  _fingerprint_for_action(action, params) — builds the state dict
  from cwd, referenced file mtimes/sizes, disk-free bucket (10%
  steps so minor fluctuations don't invalidate).
  _drop_volatile(state) — removes the ts_bucket_min field before
  hashing so the fingerprint is stable across the deferral window.
  11/11 offline self-test cases pass.

KNOWN REMAINING FOLLOW-UPS FROM THIS SESSION
========================================

- Production verification of the card path requires a live Telegram
  interaction from the owner. Saying "install cowsay" or "write a test
  note to /tmp/foo.txt" should produce a transcript line plus a
  second Telegram message with the formatted card, then yes/no
  should actually execute/refuse. Not tested end-to-end yet.

- The pipeline's _fingerprint_for_action includes cwd. the owner's
  shell cwd won't match the daemon's cwd; this is fine because the
  fingerprint is stable across deferral but worth noting for the
  edge case of approvals that span restarts — a daemon restart
  changes cwd and would expire any pending cards. Graceful, but
  potentially surprising. Could mitigate by dropping cwd from the
  fingerprint.

- The self-mod dialog's "answerer" callable is currently passed a
  placeholder that returns "I've noted your question. When you're
  ready, reply with the exact ratification phrase above." Wiring
  it to Maez's main brain for real back-and-forth Q&A is a Part 3
  task.

- Telegram reaction webhook (setMessageReaction / message_reaction
  updates) is not wired. The reply classifier already handles
  reaction emoji; the webhook just needs to be enabled in the
  bot's allowed_updates and a handler added to receive
  message_reaction updates.

- Stale LoRA-rut issue inherited from Session 11y: cycles 7-8
  flagged "a significant number of uncommitted changes in your
  maez repository" despite the uncommitted changes just having
  been committed. Perception cache lag, not a new bug.
