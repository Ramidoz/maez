SIGTERM/SIGKILL finding — separate diagnostic slice
================================================================================

During M1 enablement, restarting maez.service required SIGKILL after SIGTERM
failed to stop the process cleanly within systemd's grace window.

Investigation by operator:
  - SIGTERM was received and clean shutdown began.
  - Telegram, WebSocket, health endpoint, planning, consolidation, and
    journal threads all stopped cleanly.
  - Process stayed alive until systemd/user killed it.
  - Live maez process has 296 threads at idle, mostly:
    - tokio-rt-worker (Rust async runtime)
    - sqlx-sqlite-worker (Rust SQLite via sqlx)
    - reasoning-loop-named native threads
    - a few executor threads
  - M1 lock NOT in the shutdown path.
  - No M1 flush/promotion logs at shutdown time.

Conclusion: NOT M1-attributed. The likelier cause is broader daemon
shutdown / native-thread / shared-executor issue, probably from
Rust-backed library threads that don't exit cleanly on SIGTERM. M1
enablement merely required a restart, which exposed the pre-existing
"some workers don't go home when Maez closes the shop" problem.

Queued as: daemon-shutdown diagnostic slice (not M1 recovery).
Starting hypothesis: daemon shutdown is blocked by native/background
worker threads, likely from Rust-backed libraries or shared executor
paths.
Starting evidence: clean shutdown initiation, M1 not in shutdown path,
296-thread inventory with category breakdown.
Next diagnostic goal: capture thread dump during the hang, identify
which library/thread pool refuses to exit.

Cheap commands for the diagnostic session opener:
  py-spy dump --pid $(pgrep -f maez_daemon) > /tmp/maez-hang-threads.txt
  .venv/bin/python -c "import sys; print([m for m in sys.modules if 'tokio' in m.lower() or 'sqlx' in m.lower()])"
  .venv/bin/python -c "import threading, atexit; atexit.register(lambda: [print(f'{t.name}  daemon={t.daemon}  alive={t.is_alive()}') for t in threading.enumerate()])"

(No sudo needed — maez.service is user-scoped under rohit.)

Important: M1 stays live during this work. If a flag-off reproduction
ever proves the SIGTERM issue is M1-specific, that's when the M1
recovery lane reopens — not before.
