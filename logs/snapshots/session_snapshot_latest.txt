========================================
THE HEADLINE
========================================

Presto is no longer just a loose experiment hanging off the side of
Maez. It now has a canonical home under `hardware/presto`, with host
bridge code, a body-state relay, device-app ownership, and a small
manifest that explains what the hardware is and how it connects.

The bedside remote was also redesigned away from a cramped status
dashboard. The new direction is a calmer "bedside presence" surface:
small time in the corner, one dominant state, one short prompt, a
central orb, and a tap-to-toggle details strip. The rewritten remote
was pushed to the actual board, set as launch target, and soft-reset.

========================================
WHAT CHANGED
========================================

1. Hardware module structure

- added `hardware/__init__.py`
- added `hardware/presto/__init__.py`

2. Compatibility preserved

- `scripts/presto_bridge_cli.py` now imports from `hardware/presto/bridge.py`
- `scripts/presto_body_state_server.py` now delegates to
  `hardware/presto/body_state_server.py`

This keeps the current operational path intact while giving Presto a
stable identity as hardware.

3. Device-side UI redesign

Rewrote both:

- `hardware/presto/device_apps/presto_maez_remote.py`
- `scripts/presto_maez_remote.py`

New design traits:

- assumes real Presto dimensions: `480 x 480`
- uses PicoGraphics bitmap text rather than a denser vector-heavy layout
- removes fake "face dashboard" framing
- emphasizes one human-facing status at a time
- keeps details available through touch, but not dominant

Current mode language:

- `Present`
- `I need you`
- `Stay nearby`
- `Morning hush`

These are still derived from the simple host `/body-state` payload, so
this is a first useful surface rather than the final semantic layer.

ADDENDUM — UBUNTU CRASH DEBUG / ELECTRON STABILIZATION
========================================

Ubuntu crashed again on the boot that ended at:

- `Tue 2026-04-14 13:43:40 CDT`

Evidence gathered:

- no preserved panic/oops dump in `/sys/fs/pstore` after reboot
- final previous-boot journal ends abruptly inside normal user-space
  logging, which suggests hard freeze / abrupt reset more than a clean
  daemon crash
- historical crash signals in the same general system window include:
  - NVIDIA `Xid 56` GPU faults
  - `antigravity` crashing in `watcher.node`
  - `code` segfaulting

An unrelated but important stability bug was found and fixed:

- `maez-electron.service` was hard-coded to:
  - `DISPLAY=:1`
  - `XAUTHORITY=/run/user/1000/gdm/Xauthority`
  - `Restart=always`
- the real active session was actually on:
  - `DISPLAY=:0`
  - `/run/user/1000/.mutter-Xwaylandauth.*`

Effect:

- Electron repeatedly failed to connect to the desktop session
- systemd hammer-restarted it forever, creating a persistent restart storm

Mitigation landed:

- `ui/electron/main.js`
  - disables Electron GPU acceleration
- `scripts/launch_maez_electron.sh`
  - dynamically discovers the live graphical session
- `staging/maez-electron.service`
  - uses `ExecCondition` session gating
  - uses `Restart=on-failure` instead of `Restart=always`

System change applied:

- installed corrected unit to `/etc/systemd/system/maez-electron.service`
- `systemctl daemon-reload`
- restarted service successfully

Verification:

- `maez-electron.service` now reaches `active (running)`
- restart storm is gone

Current best interpretation:

- the Electron unit bug was real and is now mitigated
- the broader Ubuntu crash still looks more like display / GPU-stack
  instability than a direct Maez daemon failure
