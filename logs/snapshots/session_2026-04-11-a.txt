========================================
ROOT CAUSE (why "who are you?" dropped for <USER_B>)
========================================

The old /chat guest_system prompt hard-coded:
  "- You only know what {display} has personally told you in your
     conversations"
  "- You know NOTHING about the owner's personal life, work, projects, or
     vision unless {display} specifically told you about it"
  "- If asked about things you don't know, say you don't know"

<USER_B> asks: "who are you?"

Gemma4 sees: "user is asking about ME (Maez). The rules say I only know
what the user told me. The user never told me anything about me. The
rules say if I don't know, say I don't know."

Result: refusal or empty reply. The empty-reply fallback at line 793
then fires with simple_msgs, and either returns the placeholder
"I'm here. What's on your mind?" or drops entirely.

The CRITICAL RULES were designed to protect the owner's privacy from raw
guests. They were NEVER meant for <USER_B> — she's the owner's partner, marked
trust_tier=3 and rohit_confirmed=1 in users.db. She had earned context.
The prompt never checked whether she had. It was strip-mining the
trust_tier variable into a prompt template string that didn't branch
on it.

========================================
THE FIX PHILOSOPHY
========================================

share_config is the privacy rail. Not hard-coded strings.

For linked users the new trusted_system prompt:
  - References the actual relationship ("They are girlfriend")
  - Drops the "know NOTHING" scripture
  - Tells Maez she may share what share_config permits
  - Keeps share_config as the SOLE enforceable boundary

If the owner wants to tighten <USER_B>'s surface, he edits her share_config in
users.db and the next request reflects the new policy. Zero code change.

For unlinked users (8 accounts in users.db today, all trust_tier=0) the
original guest_system prompt is preserved verbatim. Cold-guest rules
still apply to everyone who hasn't earned context.

========================================
ONE GAP FLAGGED FOR 11n
========================================

Cross-process backoff signal for /chat.

The _rohit_active_until backoff works for the owner's Telegram (same Python
process as daemon) but NOT for web /chat conversations — maez-web.service
is a separate systemd service in a different Python process. <USER_B>'s
web /chat calls can't signal the daemon to defer its cycle, so she
still experiences GPU contention if her message lands mid-cycle.

Cold-path test 3 hit exactly this and took 2m50s.
Warm-model retry test 3b took 2.58s.

A file-based sentinel (/tmp/maez_human_active_until) or a tiny HTTP
endpoint on the daemon would bridge this. Small change, worth doing
next session.
