========================================
BUG 1 — FALSE "FAMILIAR" TELEGRAM MATCH
========================================

Symptom:
  the owner created a web account:
    username     = rohit
    display_name = ramidoz

  The registration flow offered a "That feels familiar" / Telegram-link prompt.
  After accepting it, the account looked linked to some strange identity.

What actually happened:
  It did NOT link the owner to another person's Telegram history.
  It linked the new web account to its own freshly-created web profile.

Proof from users.db before repair:

  username     = rohit
  display_name = ramidoz
  uuid         = ced70c857b5d2655
  telegram_id  = ced70c857b5d2655

The telegram_id matched the account's own uuid, which is impossible for a
real Telegram user and proves this was a self-link, not a stranger-link.

Root cause:

  skills/web_interface.py
    POST /register:
      result = accounts.register(...)
      match  = accounts.find_possible_telegram_match(display_name, username)

  skills/user_accounts.py
    register() created a public_users profile immediately:
      user_id    = uid
      username   = rohit
      first_name = ramidoz

    find_possible_telegram_match() then searched *all* profiles, including the
    one just created, and returned the first fuzzy name match.

  Result:
    The newly-created web profile matched itself and was presented as if it
    were a pre-existing Telegram identity.

Fix:

  user_accounts.find_possible_telegram_match(...)
    + accepts exclude_user_id
    + skips candidate user_id == exclude_user_id
    + skips non-digit user_id values
    + skips candidates with message_count <= 0

  web_interface.register()
    + passes exclude_user_id=result['uuid']

Behavior after fix:
  New web signups no longer see bogus Telegram matches from their own brand-new
  profile rows. Only real Telegram identities with actual conversation history
  can be suggested.

========================================
BUG 2 — WEB COULD NOT SEE ROHIT'S REAL CONTINUITY
========================================

After clearing the bad self-link, the deeper issue became obvious:

  The web app only knew how to merge history from:
    memory/db/public_users/user_conversations

  the owner's real long-running relationship with Maez lives in:
    memory/db/raw/raw_archive
    type = telegram_exchange

So even a "linked" web account still could not actually inherit the owner's
private Telegram continuity. The data paths were different.

========================================
OWNER BRIDGE DESIGN
========================================

Goal:
  Give the owner's web account access to the same continuity lane as the private
  Telegram bot, without weakening public-user isolation for everyone else.

Implementation:

1. Explicit owner bridge marker

  skills/user_accounts.py
    PRIVATE_OWNER_PROFILE_ID = "private_owner"

    link_private_owner(uid):
      telegram_id         = MAEZ_TELEGRAM_USER_ID  (resolved as <OWNER_TELEGRAM_ID>)
      telegram_profile_id = private_owner
      rohit_confirmed     = 1
      relationship        = owner
      trust_tier          = 3
      share_config        = full Tier 3 config

    get_user_record(uid):
      returns private_owner_bridge=True when
        telegram_id == owner telegram id
        telegram_profile_id == private_owner

2. Raw-memory accessor for the owner's Telegram exchanges

  memory/memory_manager.py
    get_telegram_exchanges(limit=400)
      reads raw_archive where type == telegram_exchange
      sorts chronologically

3. Owner-aware web history

  skills/web_interface.py
    _parse_owner_exchange(...)
    _load_private_owner_history(...)

    GET /history:
      if private_owner_bridge:
        load parsed telegram_exchange memories from raw archive
      merge with any web conversations under the account uuid
      return user.owner_bridge = true

4. Owner-aware web chat

  skills/web_interface.py
    POST /chat:
      if private_owner_bridge:
        build prompt from:
          - SOUL
          - memory.recall_for_telegram(message)
          - current web turn
        treat web + private Telegram as one continuous relationship
        write reply back through memory.store_telegram(...)

      else:
        keep existing public-user isolated path unchanged

5. Truthful UI label

  ui/app.html
    owner bridge shows:
      "private continuity linked"
    ordinary linked users still show:
      "telegram history linked"

6. Future recovery path

  skills/telegram_voice.py
    /login now calls link_private_owner(...) for the authorized private bot user
    and normal link_telegram(...) for everyone else

Important nuance:
  maez.service was NOT restarted in this session, so the telegram_voice.py
  change is committed on disk but not yet active in the running private bot
  process. The bridge itself is already live because it was applied directly
  to the rohit account row and maez-web.service was restarted.
