11q — SPECULATIVE DECODING NEGATIVE RESULT
========================================

Goal: add --model-draft to main gemma-4-26B-A4B llama-server using
a small gemma-4 family draft model. Expected 2-3x generation speedup
per research.md.

Draft models tried:
  - ggml-org/gemma-4-E2B-it-GGUF — Q8_0, 4.63 GB
  - ggml-org/gemma-4-E4B-it-GGUF — Q4_K_M, 4.97 GB

Tuning configurations:

Config 1: E2B, default tuning
  --draft-max 16 --draft-min 5 --draft-p-min 0.75
  Acceptance: 40.3% (25 accepted / 62 generated)
  Generation: 31 tok/s (117 tok/s baseline — 73% SLOWER)
  Verdict: NEGATIVE

Config 2: E2B, conservative tuning
  --draft-max 8 --draft-min 3 --draft-p-min 0.90
  Acceptance: 59.3%
  Generation: 71 tok/s (39% SLOWER than baseline)
  Verdict: NEGATIVE

Config 3: E4B, conservative tuning
  --draft-max 8 --draft-min 3 --draft-p-min 0.90
  Acceptance: 61.5%
  Generation: 64 tok/s (45% SLOWER than baseline)
  Verdict: NEGATIVE (E4B being bigger hurt draft cost,
  only 2 points of acceptance improvement over E2B)

Root cause hypothesis:
  gemma-4 is a sparse MoE family where each variant (E2B, E4B,
  26B-A4B, 31B) has independent expert routing. Draft model token
  predictions need to correlate tightly with main model token
  distribution for spec decoding to net-win. MoE expert
  divergence between draft and main keeps acceptance stuck
  around 60%. Break-even is ~70%. No gemma-4 family draft
  reached that.

No viable alternative drafts:
  - Cross-family drafts (qwen, llama) are tokenizer-incompatible
  - gemma-4-31B is larger than main, can't be draft
  - No dense gemma-4 variant below 26B exists

Secondary constraint discovered:
  llama.cpp ff5ef82 refuses to start llama-server with both
  --mmproj and --model-draft. Error:
    srv load_model: speculative decoding is not supported with
    multimodal
  Workaround: vision lives on a separate server anyway (see 11r).

Decision: revert llama-server.service to 11p baseline. 11p's
117-137 tok/s generation, 6238 tok/s prompt eval, 3.17s daemon
cycles still stand.

Files ultimately touched by 11q:
  /etc/systemd/system/llama-server.service
  (temporarily added draft flags, then reverted)

Code shipped: ZERO.

Draft model files left on disk (~9.6 GB, kept for possible

11r — VISION UPGRADE: gemma4 mmproj → Qwen2.5-VL-3B
========================================

the owner's question during 11q: "there must be better models for
vision — what do you suggest?"

Answer: YES. gemma-4 mmproj is a general-purpose vision attachment
on a general-purpose LLM. Purpose-built small VLMs are both higher
quality AND smaller VRAM.

Chosen: ggml-org/Qwen2.5-VL-3B-Instruct-GGUF
  Reasons:
    - Same org as gemma-4-26B — proven llama.cpp compatibility
    - Small: 3B params, ~2.5 GB VRAM total
    - Purpose-built for visual description + OCR + structured output
    - Q4_K_M available

Downloaded:
  Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf          1.80 GB
  mmproj-Qwen2.5-VL-3B-Instruct-Q8_0.gguf     0.79 GB
  Total                                       2.59 GB
  Staged at /home/rohit/maez/models/llamacpp/

New systemd unit:
  /etc/systemd/system/llama-server-vision.service
  Port: 127.0.0.1:8081
  User: rohit
  Restart: always
  Enabled at boot
  Log: /var/log/llama-server-vision.log
  Flags: -m Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf
         --mmproj mmproj-Qwen2.5-VL-3B-Instruct-Q8_0.gguf
         -ngl 999 --ctx-size 8192 --parallel 1
         --flash-attn on --cache-type-k q8_0 --cache-type-v q8_0
         --alias qwen2.5-vl-3b --cont-batching --jinja

VRAM architecture change:
  Main llama-server.service: dropped --mmproj flag.
  Before: main server carried gemma4 + mmproj for future vision
          use (wasted 1.1 GB).
  After:  main = text only, vision = dedicated Qwen2.5-VL-3B.

  pre:  git_workflow 43%
  post: git_workflow 76%

Raw interpretation: looks like a regression. 9-point mean score
drop, fixation label exploded, z-statistic ~5.5 on mean
difference.

But data is HEAVILY CONFOUNDED:

The 55 minutes of post-migration cycles all happened during an
extraordinarily narrow work context — the owner reviewing Maez
technical decisions, git operations, VS Code + terminal + browser
on the same project, me watching him work, him watching me work.
76% of post cycles landed on git_workflow as primary topic vs 43%
pre-migration (which spanned 3 days across varied activities:
sleep, morning briefings, different coding sessions, Telegram
conversations, screen perception on different apps, different
times of day).

The cognition system explicitly penalizes topic fixation. When
ground-truth observations are all about the same thing for an
hour, the fixation label fires CORRECTLY. The 42.9-point
fixation jump is the anti-fixation rail working as designed, not
evidence that the new brain reasons worse.

Two POSITIVE signals that push against the regression hypothesis:

1. 'vague' label dropped 21 points (63% -> 41%). Post-migration
   thoughts are measurably MORE SPECIFIC than pre-migration.
   If the brain were worse, we'd expect vague to go UP, not down.
   Unambiguous improvement signal.

2. 'actionable' label held steady (86% -> 84%). The core quality
   signal (does Maez produce useful observations?) barely moved.
   Actionable stayed dominant in both samples.

What I can say confidently:
  [x] The brain isn't broken.
  [x] All labels + primary categories producing as expected.
  [x] Observation quality is MORE specific, not less.
  [x] Fixation spike is a workload artifact, not reasoning drift.

What I cannot say from 87 cycles:
  [ ] Whether the -9.1 mean drop is substrate-caused or
      workload-caused.
  [ ] Whether observed differences persist across diverse contexts.
  [ ] Whether gemma-4-26B-A4B on llama.cpp is genuinely as good
      as gemma4:26b on Ollama for steady-state use.

VERDICT: INCONCLUSIVE.

Need 500+ post-migration cycles across genuinely varied work
contexts (1-2 days of real use with different times of day,
different activities, different kinds of conversation) before
a clean comparison is possible.

Recommendation: accept migration as provisionally-stable,
continue operation, revisit in a dedicated observation session
later. Reverting to Ollama based on 87 confounded cycles would
be premature and also impossible in practice (most ollama code
paths are now migrated).
