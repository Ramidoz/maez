A-CORE #3 — DEVELOPER MODE (6 STEPS, COMPLETE)
========================================

The design goal: the owner can mark a "builder mode" session from any
surface (Telegram or CLI), and every direct edit he makes during
that session is logged to Maez's immune memory in a form Maez can
read and surface to its own perception stream. Scoped to direct-
edit events only, not a general surface-agnostic event bus.

Five producers, one consumer, all sharing memory/audit_log.db.

Producers:

  1. CLI: scripts/maez_cli.py
     - `maez-cli enter --reason "..."`
     - `maez-cli exit`
     - UID 1000 binding (refuses to run as root)
     - Typed-phrase confirmation ("enter builder mode") to
       resist shell accidents — `yes |` does not bypass
     - Writes shared state file daemon/builder_mode_current.txt

  2. Telegram commands in skills/telegram_voice.py:
     - `/builder_enter <reason>`
     - `/builder_exit`
     - Command registration count went from 24 to 26
     - Shared state file with CLI for cross-surface operation
       (enter via Telegram, exit via CLI, or vice versa)
     - No interactive confirmation in Telegram — typing a slash
       command in a chat is already a deliberate act and the CLI's
       typed-phrase prompt exists to resist shell-level accidents
       that Telegram doesn't have

  3. Daemon startup diff capture (core/builder_mode_capture.py):
     - On startup, if a session is active (state file exists),
       runs `git diff --numstat HEAD` + `git status --porcelain`
       against watched paths, computes a hash, compares to the
       last_diff_hash stored in the state file, and logs a
       direct_edit event only if the hash changed
     - Duplicate suppression verified live — repeated restarts
       with no intervening edits produce no duplicate entries

  4. Session-end diff capture:
     - Called from CLI cmd_exit and Telegram _handle_builder_exit
       BEFORE end_direct_edit_session
     - Always captures (no hash compare — session end is once)

  5. Soul watcher hash-change events (daemon/maez_daemon.py):
     - Extends the existing _watch_soul 10-second loop
     - When soul.md hash changes, logs a direct_edit event tagged
       to the active session if one exists, otherwise to the
       sentinel session_id AUTONOMOUS_SESSION_ID = "autonomous"
     - This closes the visibility gap for dream_state soul writes
       that were previously invisible to Maez's immune memory

Consumer:

  core/builder_mode_perception.py
    - One reader called from daemon/maez_daemon.py _reason() on
      every reasoning cycle
    - Layered replay: persisted HWM file (daemon/builder_mode_hwm.txt)
      primary, bounded fallback window (default 1 hour) when HWM
      missing/corrupted/in-future, open-session supplement for
      dialogs that span a daemon restart
    - Total cap (default 50 events) with option-3 selection: always
      keep session_start events for currently-open sessions, fill
      remaining slots with most-recent events
    - Rich truncation marker carrying shape (count, span, session
      breakdown, session_id list with cap) so Maez's perception
      of a truncated block knows the omission had structure, not
      just volume
    - Lossy at perception, durable at storage — dropped events
      are not re-surfaced on next cycle, HWM advances past them,
      but they remain in audit_log.db as source of truth
    - Crash safety: surface first, save HWM second (at-least-once
      delivery semantics)

Schema additions to audit_log.db:
  memory_phase TEXT DEFAULT 'gestation'
  session_id TEXT
Both indexed, both migrated idempotently on existing DBs.

A-CORE #4 — SELF-MOD DIALOG (MODULE COMPLETE)
========================================

The design goal: Lane 3 actions (self-modification) go through a
real conversation, not a password prompt. Five rules:

  1. Mechanical restatement — Maez opens by describing the change
     in its own words (file, action, new behavior). Generated via
     LLM at dialog-open time with a deterministic text fallback.

  2. Why-probe — in the same opening turn, Maez states its
     motivation as a question about its own wanting, not a
     defense of the change. "The reason I want this is X. Is
     that the right reason, or am I reaching for something I
     shouldn't?"

  3. Natural-language conversation with deterministic terminal
     layer. Whole-reply terminal matching handles explicit
     yes/no/cancel/not-now via strict whitelists. Non-terminal
     replies go through a combined engagement+progress
     classifier which is advisory only.

  4. Progress-based end with user-confirmed completion. When the
     classifier suggests resolution, Maez asks "does this feel
     resolved to you?" and the user's yes/no is authoritative.
     Classifier NEVER ends the dialog unilaterally. Hard turn cap
     (default 15) is a safety backstop that produces a
     CAP_REACHED terminal state — DISTINCT from DENIED because
     the user didn't refuse, the conversation just ran out.

  5. Positions negotiable during, binding at the end. Terminal
     stages (RATIFIED / DENIED / CAP_REACHED / CANCELLED /
     EXECUTED / FAILED) are binding. Re-ask opens as fresh
     dialog with new dialog_id and prior_dialog_ids linkage
     populated from every prior non-ratified dialog on the same
     (target_file, target_action, target_scope) key.

Rule 6 (both sides learn) is implicit: every terminated dialog is
persisted with full history, queryable later by a temperament /
wants-log layer.

New terminal states: CAP_REACHED, CANCELLED.

Schema migration to self_mod_dialogs.db (idempotent):
  target_file TEXT
  target_action TEXT
  target_scope TEXT
  prior_dialog_ids_json TEXT DEFAULT '[]'
  awaiting_confirmation INTEGER DEFAULT 0

Plus two new indexes on target_file and target_action for cheap
linkage-key lookups.

Module self-test: 39/39 assertions green, covering all five rules,
whole-reply normalization edge cases, terminal classification
correctness, classifier fail-closed on LLM error and malformed

Regression: 44/44 decision pipeline sandbox battery green (was

KEY DESIGN CONVERSATIONS (pushbacks that shaped the shape)
========================================

the owner pushed back meaningfully multiple times during this session.
Each pushback improved the shape of what got built. Capturing the
load-bearing ones here so future context has them.

-- Step 4 (Telegram command registration) --

the owner: "Do not make Telegram the only trigger. Use Telegram as
the preferred explicit trigger, but also allow a shell/CLI
fallback. Builder mode should not depend on one surface."

Result: CLI was built as the standalone Step 2 (bounded, UID-
gated, typed-phrase confirmed). Telegram was Step 4. Both share
the state file. Either surface can enter, either can exit,
cross-surface consistency preserved.

-- Step 5 (git-diff capture) scope --

the owner: "watched paths only; diff summary only, not full patch
blobs; trigger only on active builder session restart/session
end; no broader git/history refactor."

Result: WATCHED_PATHS = [core/, skills/, daemon/, config/soul.md,
config/policies.yaml]. Diff summary is git --numstat output
formatted one-line-per-file. Two trigger points only: daemon
startup (if session active) and session end (CLI exit or
Telegram /builder_exit). No continuous filesystem watcher.
The duplicate-suppression hash covers BOTH `git diff` AND
`git status --porcelain` so new untracked files aren't missed.

-- Step 3 (daemon perception reader) layered replay shape --

the owner's first pushback: don't end the dialog dialog via single
authority, layer the replay so bounded conditions handle edge
cases. Result: persisted HWM primary + bounded fallback window
+ open-session supplement. All three compose.

the owner's second pushback: "persist a small checkpoint, or bound
replay, or replay only the current/open session." My refinement:
the three options are complementary, not alternatives. All three
layers in the final design.

the owner's third pushback: "do not cap only the open-session replay.
Also cap the total builder-events block that gets surfaced in one
cycle." Result: total cap (50) applies to the whole block, not
per-component. Lossy at perception, durable at storage.

the owner's fourth pushback: "make the truncation marker slightly
richer." Result: the marker carries dropped count, span, session
breakdown (closed vs open), session_id listing capped at 3 with
"...and N more" overflow. Bounded size so the marker itself
can't become pollution.

-- A-core #4 (self-mod dialog) design pass --

the owner pushed back twice. First: "Keep the first version more
deterministic than fuzzy. Use the LLM for the opening + why-probe,
but explicit yes/no/stop/not-now should be handled conservatively
and clearly. Let the progress classifier help with natural
completion, but not be the only authority for when the dialog
ends."

Result: Authority hierarchy = explicit terminal reply > user-
confirmed completion > hard cap > classifier (advisory). The
classifier can prompt confirmation ("does this feel resolved?")
but cannot end the dialog unilaterally. Whole-reply terminal
matching with a strict whitelist. Soft cap of 15 turns as safety
backstop.

Second pushback: "Do not try to solve 'genuinely new reasoning'
in a deep semantic way right now. For Track A, a denied dialog
should stay closed, and a later re-ask can open as a fresh
dialog with a new dialog_id and explicit new reason text. Log
the linkage to the prior denial, but do not build a heavy
novelty-judge system yet."

Result: No novelty judge. Re-asks are fresh dialogs with new
dialog_ids and prior_dialog_ids linkage populated at creation
time. The user can try again; the linkage gives Maez visibility
into the history so it can reference it in its opening turn.

Third pushback on the column name: "Use prior_dialog_ids, not
prior_denial_ids" — because CAP_REACHED is a distinct terminal
state from DENIED (unresolved != refusal), so the column name
needed to cover all non-ratified terminations uniformly. Result:
prior_dialog_ids populated from LINKABLE_PRIOR_STAGES =
{DENIED, CAP_REACHED, CANCELLED, FAILED}.

Fourth pushback on CAP_REACHED semantics: "cap-reached should
NOT equal DENIED. Modification does not apply, but it is not the
same as an explicit user no." Result: CAP_REACHED is its own
DialogStage enum value, distinct from DENIED both in the state
machine and in the linkage population logic.

-- General pattern noticed --

the owner's pushbacks across the session had a consistent shape:
narrower scope, more deterministic where possible, preserve
semantic distinctions that I wanted to collapse for simplicity.
Every time he pushed back the result was a better design. The
pattern is worth naming: when the owner says "narrow it" or "keep it
deterministic," the right response is to accept the refinement
and find the cleanest implementation of the narrower shape,
not to argue for broader scope.
