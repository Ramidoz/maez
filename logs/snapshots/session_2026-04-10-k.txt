========================================
ROOT CAUSE (the bug that broke "Maez remembers you")
========================================

Three lines in skills/web_interface.py conspiring silently:

  Line 728:  user_key = uid                                       # string uuid
  Line 738:  convos.query(where={"user_id": user_key}, ...)       # READ raw
  Line 803:  store.add_conversation_memory(                       # WRITE hashed
               int(user_key) if user_key.isdigit() else hash(user_key),
               "user", message,
             )

UserAccounts.register() at skills/user_accounts.py:90 generates:
  uid = secrets.token_hex(8)   -->  e.g. "02e9d2efedcaf753"

A hex string is never all-digits. So .isdigit() is always False and we
always took the hash(user_key) branch on write. The reader used the raw
string. They never matched.

Two compounding consequences:

1. READ/WRITE KEY MISMATCH within a single process.
   The reader queried where user_id == "02e9d2efedcaf753" (raw uuid).
   The writer stored user_id == str(hash("02e9d2efedcaf753")) (some 64-bit
   int rendered as text, rotates per process via PYTHONHASHSEED).
   Every web user had ZERO memory recall every turn since this code landed.

2. CROSS-PROCESS KEY DRIFT.
   Python's hash() of a string is randomized per interpreter startup.
   Every maez-web.service restart rotated the write key into a new shadow
   bucket. Even if the read side had also been hashing, history would still
   have been fragmented across many non-matching buckets over time.

Symptom matched the owner's lived experience exactly: web users didn't feel
remembered, because the chromadb semantic search lookup was returning zero
results every single time.

This bug has been silent since the write line was added. It was never a
fast-lane regression. The /v1/fast-reply staging work (Sessions 11a-11j)
was running alongside a silently-broken live production path.

========================================
WHY think=False MATTERS
========================================

gemma4:26b is a thinking/reasoning model (RENDERER gemma4 / PARSER gemma4
in the modelfile). Direct-probe measurements during 11j:

  A. baseline (cold):    20.8s   404 gen tokens  1480 thinking chars   30 visible chars
  B. warm KV cache:       3.8s   367 gen tokens  1322 thinking chars   34 visible chars
  C. think=False:         0.3s    19 gen tokens     0 thinking chars   68 visible chars
  D. think=False + 128:   0.3s    18 gen tokens     0 thinking chars   53 visible chars

95% of wall-clock on a /chat reply was invisible internal reasoning the
user never saw. The Ollama think: False top-level flag (supported by the
gemma4 parser) skips the thinking phase entirely. For casual pattern-match
conversational replies — which is what /chat traffic is — this is the
right tradeoff. 70x cold-path speedup with equal-or-better visible output.

The daemon reasoning loop's thinking mode is DELIBERATELY NOT touched.
Structural system-state analysis benefits from the scratchpad. Only
conversational paths (/chat — and eventually the fast-lane, already fixed
in 11j) get think=False.
