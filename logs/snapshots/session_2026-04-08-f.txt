WHAT WENT WRONG / RIGHT:

WRONG — systemctl restart timeout:
The daemon has multiple threads with 60-second sleep loops. systemctl restart
waits for graceful shutdown which takes >90 seconds. First Proof 5 attempt
failed because the rail's subprocess.run timeout was 30s (then 90s). Fixed by
replacing all restart calls with kill -SIGKILL + reset-failed + start, which
completes in ~5 seconds. This is the correct approach for a daemon that
prioritizes always-on over graceful shutdown.

WRONG — LLM-generated diff quality:
The dry-run CLI (Proof 2) asked gemma4 for a unified diff. It produced
malformed output that failed patch --dry-run. The rail correctly rejected it.
This confirms the rail's value: even when the LLM makes mistakes, the
validation pipeline catches them before any file is touched. For production
use, the diff generation prompt needs refinement, or diffs should be
hand-crafted until LLM diff quality improves.

RIGHT — Immediate rollback speed:
Proof 4 showed the full immediate rollback path: bad patch applied →
py_compile failed → backup restored → service restarted → health verified,
all within seconds. The file hash returned to exact baseline. No manual
intervention needed.

RIGHT — DB as authority:
Every candidate lifecycle event is recorded in SQLite. Lock state, rollback
reasons, score averages, timestamps — all queryable. The rail never relies
on in-memory state for safety decisions. stale lock recovery works even
after manual DB corruption (Proof 1).

Layer 2 (delayed): score regression → delayed rollback via existing
daemon cadence. Both layers release the lock. Both restore from backup.
