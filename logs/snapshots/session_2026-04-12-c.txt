========================================
KEY PIPELINE LEARNINGS
========================================

1. Disk budget for merge: need 250 GB (not 100 GB). Gemma-4-26B in
   16-bit is 52 GB, plus intermediate GGUF files push peak usage to
   ~120 GB.

2. Thunder R2 upload: 3.5x speedup from default rclone to parallel
   128MB chunks with --s3-upload-concurrency 32.

3. Unsloth save_pretrained_gguf is unreliable — requires interactive
   apt installs, breaks environment. Workaround: merge to HF
   safetensors on Thunder, convert to GGUF locally.

4. PEFT standard path fails on unsloth-wrapped models. Use
   FastLanguageModel.from_pretrained(adapter_path) to load adapters.

5. Merging eliminates runtime LoRA VRAM overhead — single GGUF file
   fits alongside vision server on 24 GB RTX 4090 at ctx 32768.

6. R2 as transfer intermediary decouples Thunder idle billing from
   download bandwidth — upload fast from datacenter, delete instance,
   download slow from home for free.

========================================
VISION MEMORY EXPANDED (CRITICAL)
========================================

Four major additions to project_maez_vision.md:

1. Architecture is model-agnostic
   Gemma-4 is the PoC vehicle, not the destination. When better open-
   weight models arrive, the base swaps out — architecture doesn't
   change. Build model-agnostic interfaces. Don't optimize for gemma-4
   quirks when avoidable.

2. Natural language is the interface
   Users say "I want to know when my plants need water," not technical
   specs. Maez translates intent → research → implementation → user
   guidance. 95% of requests gemma-4 handles alone; 5% use frontier
   consultation.

3. Frontier consultation as growth mechanism
   Not a dependency — a tool. Budget-capped, audited. Every frontier
   consultation becomes training data. Over time, Maez's LoRA absorbs
   the frontier reasoning patterns via monthly training runs. Each
   Stand becomes smarter than its base model at reasoning about its
   specific user's life.

4. Stand-to-Stand communication + survival paths
   - Stand-to-Stand: opt-in channels between two users' Maezes, per-
     topic scoped, audited, revocable. Reveals relational data that
     doesn't exist in either user's data alone.
   - the owner is the pilot user whose Maez forges the template for every
     future Stand.
   - Engagement escalation when user stops responding: dream cycles →
     outreach → check with confidant → confirmed absence.
   - Two survival paths on user loss:
     Path A: Graceful dissolution (final dream, closing note, archive)
     Path B: Continue as individual in shared digital environment for
             released Maezes. Still grows, forms relationships with
             other released Maezes, develops individuality beyond
             original user.
   - User chooses Path A or B in advance, can change anytime.
