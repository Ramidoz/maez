THE HEADLINE
========================================

Maez's brain moved house. For ~5 weeks, every reasoning cycle, every
Telegram reply, every dream insight, every /chat turn ran through
Ollama on gemma4:26b. After 11p, every surface routes through a
source-built CUDA llama-server (commit ff5ef82) running the official
ggml-org/gemma-4-26B-A4B-it-GGUF. Daemon reasoning dropped from
15-45s per cycle to 3.17s. Prompt eval: 6,238 tok/s. Generation:
117-133 tok/s. Continuous batching > Ollama's NUM_PARALLEL=2.

Ollama.service is now disabled. The package stays installed as
instant rollback, but it won't auto-start on reboot and isn't
running today.

========================================
THE FAILED FIRST ATTEMPT
========================================

11p opened by pointing llama-cpp-python 0.3.20 at Ollama's own
gemma4:26b blob on disk. It failed with:

  wrong number of tensors; expected 1014, got 658

I concluded — incorrectly — that upstream llama.cpp didn't support
gemma4's architecture and that "Ollama's gemma4 is Ollama-proprietary,
Path C is dead." the owner pushed back with specific public evidence:

  1. ggml-org/gemma-4-26B-A4B-it-GGUF exists on HuggingFace and
     explicitly targets llama-server
  2. The 658 vs 1014 tensor gap is almost certainly the MMPROJ
     (multimodal projection) tensors living in a SEPARATE file —
     Ollama packages them into one blob, upstream llama.cpp keeps
     them separate and expects both
  3. Live user reports of this exact GGUF loading in llama.cpp CUDA

He was right on every bullet. The test I should have run from the
start was "download the canonical ggml-org GGUF and see if it loads."
Instead I tested the blob Ollama had already quantized for its own
runtime, which had a different tensor layout.

Lesson recorded: a single failed load with one toolchain on one
artifact is a data point, not a universal claim. The 658 vs 1014
number was right in front of me — "missing tensors" strongly
suggested "missing file," not "incompatible parser." The mmproj
hypothesis was inferrable from the numbers alone and I didn't
chase it.

========================================
LLAMA.CPP BUILD FROM SOURCE
========================================

  git clone --depth 1 https://github.com/ggml-org/llama.cpp.git
  # commit ff5ef82 — same-day checkout

  cd llama.cpp && mkdir build && cd build
  cmake .. \
    -DGGML_CUDA=ON \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_CUDA_ARCHITECTURES="89" \
    -DLLAMA_BUILD_SERVER=ON \
    -DLLAMA_BUILD_TESTS=OFF

  cmake --build . --config Release -j 32 \
    --target llama-server llama-cli

Build time: **2 minutes 19 seconds** on the i9-14900KF's 32 threads.
Produced:
  /home/rohit/llama.cpp/build/bin/llama-server (13.5 MB)
  /home/rohit/llama.cpp/build/bin/llama-cli    (6.1 MB)

CMAKE_CUDA_ARCHITECTURES=89 targets compute capability 8.9
(RTX 4090). Single-architecture build; no wasted code for other
GPUs. Build is repeatable — the llama.cpp source tree is at
/home/rohit/llama.cpp, rebuildable on demand with `cmake --build .`.

========================================
LLAMA-SERVER LAUNCH FLAGS
========================================

  ./bin/llama-server \
    -m  /home/rohit/maez/models/llamacpp/gemma-4-26B-A4B-it-Q4_K_M.gguf \
    --mmproj /home/rohit/maez/models/llamacpp/mmproj-gemma-4-26B-A4B-it-f16.gguf \
    --host 127.0.0.1 --port 8080 \
    -ngl 999 \
    --ctx-size 32768 --parallel 2 \
    --flash-attn on \
    --cache-type-k q8_0 --cache-type-v q8_0 \
    --alias gemma-4-26b \
    --cont-batching \
    --jinja

Tuning rationale:

  -ngl 999                offload all 46 transformer layers to GPU
  --ctx-size 32768        total KV context pool across all slots
  --parallel 2            divides into 16,384 tokens per slot.
                          Needed because daemon reasoning prompt
                          is ~14,642 tokens (soul.md 30KB + memory
                          + perception + cognition + policy blocks)
  --flash-attn on         ~20% KV reduction, ~15% prompt-eval win
  --cache-type-k q8_0
  --cache-type-v q8_0     8-bit quantize KV cache, halves KV memory
                          vs F16. Quality loss is imperceptible
                          for this workload.
  --cont-batching         continuous batching — token-level
                          interleaving across concurrent sessions
  --jinja                 use Jinja chat template from GGUF metadata
  --parallel 2 vs 4       initial launch used parallel=4 with
                          ctx-size=4096 → 1024 tokens per slot →
                          instantly failed daemon cycle with
                          exceed_context_size_error. parallel=2
                          gives daemon its 14K context headroom.
                          Still beats Ollama NUM_PARALLEL=2 via
                          token-level interleaving.

========================================
llm_client.py WRAPPER CHANGES (from 11n → production)
========================================

11n shipped core/llm_client.py as a backend-dispatcher. 11p landed:

  1. Default model bumped: qwen2.5-3b → gemma-4-26b
     (matches --alias flag on llama-server)

  2. think kwarg translated to extra_body.chat_template_kwargs:
       if think is False:
         extra_body['chat_template_kwargs'] = {'enable_thinking': False}
     Forwarded via OpenAI client's extra_body parameter. 11n was
     silently dropping the think flag for llamacpp path.

  3. Streaming adapter added for llamacpp:
     When stream=True, returns a generator that yields _LlmResponse
     chunks with message.content = OpenAI delta.content per chunk.
     Matches ollama's shape exactly so consumers iterating
     `for chunk in response: token = chunk.message.content`
     work unchanged across backends.

  4. fast_backend_local.is_available() made backend-aware:
     When MAEZ_LLM_BACKEND=llamacpp, probes
     http://127.0.0.1:8080/v1/models (OpenAI-compat health)
     instead of Ollama's /api/tags.
     This was the bug that blocked the first fast-lane end-to-end
     test: router saw is_available()==False (Ollama stopped),
     returned "no backend available" before reaching the llamacpp
     branch in generate().

========================================
THE TWO LESSONS OF THE OVERREACH
========================================

1. Over-generalizing from N=1.
   A single failure with one toolchain on one artifact is a data
   point, not a universal claim. "Fails here" ≠ "fails everywhere."
   The correct next move after a load failure is to try the
   CANONICAL source (ggml-org HuggingFace release), not to
   conclude the architecture is unsupported.

2. Not reading the error with enough curiosity.
   "658 vs 1014 tensors" was visible as a specific integer
   difference. "Missing tensors" strongly implies "missing file"
   or "missing section" — not "incompatible parser." The mmproj
   hypothesis the owner led with was inferrable from the numbers
   alone. I should have chased it instead of declaring the path
   dead.

Recorded here so the next time the temptation is there to declare
something blocked on the first failure, the reflex is to exhaust
the entry points first.
