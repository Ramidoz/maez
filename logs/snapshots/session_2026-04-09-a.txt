========================================
ROOT CAUSE:
========================================
Telegram message truncation lived in daemon/maez_daemon.py line 1602:

  fu_resp = ollama.chat(
      model=MODEL,
      messages=[...],
      options={"temperature": 0.5, "num_predict": 200},  # ← TOO LOW
  )

The follow-up delivery prompt called gemma4 with num_predict=200. Gemma4 is
a thinking model that consumes ~1500-2000 tokens internally before producing
visible content. With only 200 tokens of total budget, the visible output
either came back empty or got cut off mid-sentence.

This is the SAME bug pattern that hit:
- Session 4 web_interface.py (num_predict=200, fixed to 4096)
- Session 9 cognition resume_instructions (num_predict=100, fixed to 4096)

The Telegram API itself (4096 char limit) was never the bottleneck —
the model output was already truncated before send. The fix is upstream
in the Ollama call, not in the Telegram send path.

Defense layer added anyway: split_long_message() now wraps send_message()
so any future >4000 char message splits cleanly on sentence boundaries.

WHAT WENT WRONG / RIGHT:
========================================

RIGHT — Root cause fix at the source:
The bug was a 200-token Ollama budget, not a Telegram API limit.
Bumping num_predict to 4096 stops the truncation at its origin.
This is the same Gemma4-thinking-model gotcha we've hit before.

RIGHT — Defense layer in place:
split_long_message() now wraps every send_message() call. Even if
future code pipes >4000 char content (unlikely now), it splits cleanly
on sentence boundaries with 0.5s delay between parts.

RIGHT — Single canonical helper for both paths:
Both the normal reply path AND followup delivery path now go through
the same telegram.send_message() which uses the split helper. No
duplicate logic.

RIGHT — Cards are compact and high-signal:
Proposal card: 8 lines max, badge emoji, before→after value, one-click
commands. Service card: 4 lines, recovery/alert distinction by emoji.
Nightly card: 5 lines, key stats only, optional autonomy line.

RIGHT — Dev bot remains outbound-only:
No new inbound handlers added to Dev bot. Cards use the same send_dev()
underneath. Dev bot keeps its operational role unchanged.

RIGHT — Existing send_dev() calls preserved:
Did not blindly rewrite every send_dev() call. Only swapped to cards
where the pattern clearly fit (proposal notification, service alerts,
nightly summary). Short alerts still use send_dev() directly.
